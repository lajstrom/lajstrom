Lajstrom is an artifact registry on top of the OCI registry you already run. One server serves
raw files, pypi, apt, maven, npm and rpm repositories, OCI artifacts and container images, and
stores every artifact as an OCI artifact in your registry. It owns no bytes, only an index, and
the index can always be rebuilt from the registry. v0.1.0 is its first release with
functionality. <!-- at tag: the release date, planned for 2026-12-04 -->

## What does not work yet

- Formats other than raw, pypi, apt, maven, npm, rpm and OCI: terraform modules (#66).
- Proxy and group repositories of pypi and maven (#67, #68); npm and oci have them.
- A web UI (#70). It is built in its own repository,
  [lajstrom-ui](https://github.com/lajstrom/lajstrom-ui); the API it reads is in this release. A
  UI served from another origin needs `server.corsOrigins` (#949).
- LDAP and SAML. OIDC is the one login besides local users.
- maven SNAPSHOT versions (#80), pypi yanking (#81), apt source packages and Contents indexes (#79).
- Webhooks (#77); deny lists and quarantine (#101); encryption at rest (#114); signing keys in a
  KMS (#78).
- Deletes on GHCR through its packages API (#74).
- A snapshot of the control plane into the registry (#76): see "Known limitations".

## Known limitations

- **API stability.** It is not guaranteed before 1.0: the HTTP API, the configuration and the
  CLI may change between 0.x versions ([our promise](../../README.md#our-promise-to-users)).
- **The control plane is only in the database.** `lajstrom reindex` rebuilds the packages,
  versions and files from the registry. Users, tokens, bindings, repos, keys and the audit log
  are not in the registry: back the database up, and keep the master key outside it
  ([operations.md](../operations.md#backup-and-restore)).
- **The registry's own cleanup rules** (ECR lifecycle policies, Harbor tag retention, GitLab and
  Nexus cleanup policies) must stay off the repositories under Lajstrom's prefix: Lajstrom needs
  every tag there, its journal included, and the untagged referrers
  ([operations.md](../operations.md#the-registrys-own-rules)). On ECR, `serve` warns at start
  about a lifecycle policy that would expire them.
- **Databases.** SQLite serves one replica: a second `serve` on the same file is refused. Several
  replicas need Postgres. YugabyteDB is experimental, and CockroachDB does not run the migrations (#617)
  ([databases.md](../deploy/databases.md)).
- **Throttles and bounds per replica.** The throttles of failed logins and of `/v2/token`, and
  the bounds on live `/v2` upload sessions, count per replica. The edge is the bound across
  replicas ([reverse-proxy.md](../reverse-proxy.md)).
- **The audit log** only grows: there is no retention or export yet. It is part of the backup of
  the index.
- **`server.externalURL`** must be https; plain http is accepted only on a loopback host, with
  `server.insecureHTTP: true`.
- **Uploads are bounded by default** (#246). A file or a `/v2` blob above its format's size is
  `413`: npm 512 MiB, pypi and maven 4 GiB, apt, raw and rpm 8 GiB, oci 16 GiB, or the
  registry's `maxBlobSize` when smaller (GHCR's 10 GB); a repo's `policy.maxFileSize` sets
  another size, higher or lower: an `oci` repo of ML models needs 64 to 256 GiB, and the
  registry and the edge must take such blobs too
  ([operations.md](../operations.md#large-blobs-ml-models)). A replica runs 32 uploads at once
  (`server.maxConcurrentUploads`, `0` lifts it), a principal holds at most 256 live `/v2` upload
  sessions of a repo and 1024 of all repos on a replica (`server.uploadSessions`), and a Maven
  deploy stores at most 256 files (`policy.maven.maxSessionFiles`).
  [operations.md](../operations.md#requests-from-clients) lists every bound.
- **The `repos[]` bootstrap** of the configuration creates repos and never changes or deletes
  one; the API does that.
- **The Helm chart's** HTTPRoute, Ingress, ServiceMonitor and autoscaler were checked against
  their schemas, not installed on a cluster; Argo CD and Flux were not tried
  ([helm.md](../deploy/helm.md#what-was-not-verified)).

## Upgrade

v0.1.0 is the first release with functionality. v0.0.1 only reserved the name: it has no server
and no index schema. So:

- **There is nothing to upgrade from.** Install v0.1.0 as new ([install.md](../install.md),
  [compose](../deploy/compose.md), [helm](../deploy/helm.md)). `serve` applies the index
  migrations, 0001 to 0021, at its first start, or `lajstrom migrate` before it; none of them is
  a contract migration. <!-- at tag: the last migration of the tagged commit, ls internal/index/migrations/postgres | tail -1, and that none has a "-- lajstrom:requires" line -->
- **A build of `main` from before the tag** is not a release, and no upgrade from one is tested
  or promised. Back up its database before you run v0.1.0 on it. Three late changes break
  scripts written for such a build: `LAJSTROM_ADMIN_PASSWORD` is gone (`lajstrom admin user
  create` and `set-password` fail while it is set; the first admin comes from a bootstrap
  token, [operations.md](../operations.md#the-first-admin)); a `401` of `/api/v1` has the code
  `UNAUTHENTICATED`, not `FORBIDDEN`; and `database.driver: postgres` has no default DSN.
- **From v0.1.0 on**, the notes of a release with migrations list each one and say whether it is
  expand or contract, and the release is tagged only once the Upgrade workflow ran the release
  before's binary and end-to-end suite on the schema the new one migrated
  ([release.md](../release.md#migrations-in-the-notes), [operations.md](../operations.md#upgrades)).
  Until v0.1.0 exists that workflow has nothing to run, so INV-41, "a binary runs only on a
  schema it can run on", is `partly` in [guarantees.md](../spec/guarantees.md).
