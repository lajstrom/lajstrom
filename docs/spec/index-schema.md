# Spec: index database schema

- Status: normative for the MVP (2026-11-06). Owned by `internal/index`. Column changes go
  through a new migration file; renames of derived tables are free, control-plane tables need an
  issue labelled `contract`.
- Related: [ADR 0001](../adr/0001-oci-registry-as-sole-storage.md),
  [ADR 0006](../adr/0006-derived-index-and-control-plane.md).

Two kinds of tables. **Derived** tables are rebuilt by `lajstrom reindex` from the registry, but
two that need no rebuild ([Derived](#derived)), and may be dropped at any time. **Control plane**
tables are small, authoritative and backed up, with the database or as a snapshot in the
registry ([below](#snapshots-of-the-control-plane)). The **coordination** tables, `tag_claims`,
`reindex_runs`, `fetch_claims`, `replicas` and `oidc_logins`, are neither: their rows live for one
publish, one fetch, one `serve` process or one OIDC login, and a `reindex_runs` row is the lock of its run while it runs, then
its record (the ten newest finished runs of a scope are kept).
`prune_sightings` is neither too: the operational state of prune, whose rows live from one
reindex run to a later one.
SQLite and Postgres share one logical schema; dialect differences are confined to the migration
files (`internal/index/migrations/{sqlite,postgres,cockroach}/NNNN_*.sql`). CockroachDB is a
dialect of the `postgres` driver, which selects it when the server is CockroachDB (#617;
experimental, [databases.md](../deploy/databases.md#cockroachdb)): it has migrations of its own
([Migrations](#migrations)), and what this spec says of Postgres holds for it otherwise, its
transactions asking for read committed and its locks being `pg_advisory_xact_lock`.

Types below: `id` = integer primary key (SQLite) / `bigserial` (Postgres) / `bigint GENERATED BY
DEFAULT AS IDENTITY` (CockroachDB, whose `bigserial` would not ascend from 1); `ts` = UTC
timestamp stored as RFC 3339 text in SQLite, `timestamptz` in Postgres; `json` = `text` in
SQLite, `jsonb` in Postgres. Every `json` column is nullable: NULL is "absent or empty" (`policy`,
`scopes`, `files`, `details`, `attrs`, `metadata`), and the store reads it back as nil.

### The audit row of a registry write

No transaction spans the registry and the database (#473; [guarantees.md](guarantees.md)
INV-14). A change of the index alone, or of the control plane, appends its row `ok` in its
transaction. A write to the registry (a publish, a proxied ingest, a delete, a journal entry, a
referrer, a push to an `oci` repo) has its row written twice:

- **Before the write**, in a transaction of its own, `pending`: the principal, the action, the
  repo, the subject, the digest, the client address and the request id. It comes after the
  reads that may refuse the write (the claims, the tag in the backend, the other tags of a
  manifest to delete) and before the first request that changes the registry. When it cannot
  be written, the write is not made and the request fails.
- **After the write**, completed: `ok` in the transaction that records the write in the index
  (the version, the journal entries, the `oci_repos` row; a referrer, which has no index row, in
  a transaction of its own), with the details the write learnt (the referrers a delete took,
  `existed` for a publish that another replica confirmed first); or `failed`, in a transaction
  of its own, with the error, when the registry refused or failed the write or the index
  transaction after it failed. The state is the answer: `ok` was a success, `failed` an error.
- **Unknown**: a row still `pending` whose `at` is older than `ingest.claimTTL` is a writer that
  stopped between the two, or whose database failed both. Every reindex run, the reconcile
  loop's included, sets it to `unknown` when it expires the stale tag claims: the registry may or
  may not have the write, and reindex brings the index to what it has. A writer that ends after
  that still completes its row.

`audit` stays control plane: reindex neither reads it nor needs it, `ResetDerived` leaves it, a
backup keeps it. `GET /api/v1/audit` answers the state of each row and selects by it
(`?state=unknown`). Migration `0016_audit_state.sql` adds `state`, `NOT NULL DEFAULT 'ok'`,
`error`, and the partial index `audit_pending` on `(at) WHERE state = 'pending'` of the sweep. It
only adds: a replica of the release before it, during a rolling update, reads the table by
named columns and appends its rows without a state, which are `ok`, as they were written in the
transaction of their change.

### The audit feed and its prune

The ids of `audit` (#1278; rbac.md §5) are SQLite's `INTEGER PRIMARY KEY AUTOINCREMENT`, which
never takes an id again, also after the newest rows are deleted, PostgreSQL's `bigserial` and
CockroachDB's identity column, both a sequence; a restore of a snapshot keeps the ids and moves the
sequence past the greatest ([below](#snapshots-of-the-control-plane)). So a database never uses an
id twice; one restored, from a backup or a snapshot, takes again the ids of the rows written after
its copy, which it lost. An id is taken at the insert and the row is seen at the commit, which on
SQLite come in the same order and on PostgreSQL and CockroachDB need not: rbac.md §5 says what a
reader of the feed does about it. Three methods serve the feed and the prune:

- **`ListAudit(AuditFilter)`** with `Feed` set returns the rows whose id is above the filter's
  `After`, by id ascending, at most its `Limit`, with its other conditions. It reads the primary
  key, as the list newest first reads `audit_at`.
- **`SpanAudit(before)`** counts the rows that a prune with that cut-off would delete (`at`
  before it, `state` not `pending`, and not a `push` whose subject is a digest,
  `<algorithm>:<hex>`), with the first and the last of their ids and times; one statement on
  `audit_at`.
- **`PruneAudit(before, upTo, limit)`** deletes at most `limit` of those rows whose id is at most
  `upTo`, the lowest ids first, and returns how many it deleted. Each call is a transaction of its
  own, which holds the rows it deletes (SQLite: the write lock) for one batch only.

None needs a migration. A database keeps the space of the rows deleted for its own reuse:
PostgreSQL's after a vacuum, SQLite's in its free pages, until a `VACUUM` that the operator runs.

### The access report

The access report (rbac.md §14, #1279) is one read of the Reader, `ReadAccess`, in one transaction,
read-only, as `ExportControlPlane` reads ([One moment](#snapshots-of-the-control-plane)), so that
the report is of one moment: the live users, with `owner`, without the password's hash and history;
the rows of `identity_groups` of the live users' identities whose `groups_expire_at` is after the
time of the read; every row of `bindings`; the rows of `tokens` neither revoked nor expired at that
time, the deploy tokens over a mask among them; every row of `ci_policies`; and the repos with
`anonymous_read` and those of the live deploy tokens of one repo (`TokenRepos`), which name those
tokens; with the database's time of the read as `ReadAt`. One statement per table. The report stores nothing, its
review is an audit row (rbac.md §5), and neither needs a migration.

### Pages of tokens and of open sessions

The admin's list of every token and a repo's open publication sessions (http-routing.md §4,
#959, #960) are pages of two queries of the Reader, each one statement:

- **`ListTokenPage(TokenFilter)`** returns the rows of `tokens` whose id is above the filter's
  `After`, by id, at most its `Limit`: of its kind, of its user (`user_id`), of its repo
  (`repo_id`) or over its mask (`repo_mask`, as written), each when it is set, and, when it has a
  time, those neither revoked nor expired then (`revoked_at IS NULL AND (expires_at IS NULL OR
  expires_at >= ?)`: a token that expires at that very time is live, as the authenticator takes
  it). It reads the primary key.
- **`ListOpenSessions(repoID, at, after, limit)`** returns the rows of `sessions` of the repo
  whose `state` is `open`, whose `expires_at` is after `at` and whose id is above `after`, by
  id, at most `limit`, but the blob uploads of the facade (a key that starts with
  `blob-upload:`). It reads the partial index `sessions_open_key`.

A `limit` below 1 returns none; a caller asks for one more than its page to know whether
another follows. Neither needs a migration.

### Revisions

`repos.revision`, `users.revision` and `webhooks.revision` (#796; migration
`0032_revisions.sql`, `NOT NULL DEFAULT 1`) are the revision of the row: 1 on insert, moved by
one in the statement of every update of the row (`UpdateRepo`, `ConvertRepo`, `UpdateUser`,
`UpdateWebhook`), and by nothing else. A group's `group_members` are written in the transaction
that updates its `repos` row, so its revision moves with them. The API's `ETag` names the id and
the revision of the row ([api.md](../api.md#revisions)); a change with `If-Match` compares them
with the row its transaction read, at repeatable read on Postgres, so that a change of the row
committed after the read aborts the transaction, which runs again and compares again
(`index.WithCondition`). The column is control plane, in a snapshot with its row. Expand: a
replica of a release before 0032 neither reads nor writes it, and its updates leave it as it is,
so that a change such a replica makes during a rolling update passes an `If-Match` of the
revision before it.

### A user's last activity

`users.last_seen_at` (#1283, migration `0034_users_last_seen.sql`) is the user's last activity
(rbac.md §1, Inactive users). It is written by `TouchUser` only, which only moves it forward, as
`TouchToken` moves `tokens.last_used_at` (#1277), and moves neither `revision` nor
`auth_version`: by an authentication that read it NULL or a minute old or more, by an OIDC login,
and by the enabling of the user. `CreateUser` and `UpdateUser` leave it. The column is control
plane, in a snapshot with its row.

The migration adds it and fills it for every user that is not deleted: with the time of the
migration for a user with a password, whose password logins left no record before it; for a user
without one (a service account, an OIDC user) with the latest of its tokens' `last_used_at`,
revoked and expired ones included, and of its identities' `login_at`, or NULL when it has
neither. A NULL counts from `created_at`. Expand: a replica of the release before neither reads
nor writes the column, so an authentication or an enabling on such a replica, during a rolling
update or a rollback, records nothing, and a user enabled there whose record is older than
`auth.disableInactiveUsersAfter` is disabled again at its first authentication on a replica that
knows 0034.

### The lockout

`users.password_failures` and `users.locked_until` (#1280, migration `0036_users_lockout.sql`)
are the lockout of rbac.md §1, Local passwords: the wrong passwords of the user since its last
verified password, its last lock or its last unlock, and the end of its last lock, NULL when it
has none. Three methods of the Writer write them, and nothing else does (layout.md):
`FailPassword` adds one to the count in one `UPDATE` while `locked_until` is NULL or not later
than the failure, and the failure that reaches the limit, 10, sets `locked_until` and the count
back to `0` in the same statement, so that of replicas that count at once exactly one locks;
`ResetPasswordFailures` sets the count to `0` while no lock is in force; `UnlockUser` sets it to
`0` and `locked_until` to NULL. None moves `revision` or `auth_version`, and `CreateUser` and
`UpdateUser` leave both columns. The authentication reads them with the user's row.

The migration adds both, `password_failures` `NOT NULL DEFAULT 0`: an upgrade locks no user.
Expand: a replica of the release before neither reads nor writes them, so that during a rolling
update or a rollback its failures count for nothing and a lock refuses no password there. The
columns are control plane, but not in a snapshot (below): a lock lasts a day at most, and a restore
unlocks every user.

### A password's history

`users.password_history` and `users.must_change` (#1281, migration
`0037_users_password_history.sql`) are the history and the change at first use of rbac.md §1,
Local passwords. `password_history` is a JSON list of the argon2id hashes of the user's three
passwords before the current one, each in the PHC string format of `password_hash`, the latest
first; NULL when it has none. `must_change` is true while the user's password must be changed
before it is used for anything else. `CreateUser` and `UpdateUser` write both, with the
password: a change of the password writes the new hash, the replaced one at the head of the list
cut to three, and `must_change` in one statement, and moves `revision` as every update of the row
does. Deleting a user empties its history. The columns are control plane, in a snapshot with
their row, so that a restore lets no user return to a password of its last four.

The migration adds both, `must_change` `NOT NULL DEFAULT false` and `password_history` NULL: the
first change after it compares the new password with the current one only. Expand: a replica of
the release before neither reads nor writes them, so that during a rolling update or a rollback a
password whose `must_change` is set works there, and a password set there leaves both as they
were.

### Approvals

`approvals` (#1285, migration `0039_approvals.sql`) holds the requests of rbac.md §13: a change
of the control plane that waits for a second admin, kept as the change, which its approval makes.
Nothing that reads `bindings` or `tokens` reads it, so a request grants nothing whatever reads
those. A deploy token's `change` keeps the sha256 of its secret as `hash`, as `tokens.hash` does,
and its approval inserts the `tokens` row with it. Unique `approvals_pending` on `(kind, subject)
WHERE state = 'pending'`: the same change pending twice is a conflict. Index `approvals_expires`
on `(expires_at) WHERE state = 'pending'`, which the look for expired requests reads.

`state` changes once, from `pending`, in a statement that changes it only while it is `pending`
(`DecideApproval`, `ExpireApprovals`), so that of an approval, a rejection and the replicas that
mark an expiry one decides; an approval makes its change and appends its rows in that
transaction. Rows are never deleted. They are not in a snapshot (below). The migration only
creates the table, empty: a replica of the release before neither reads nor writes it, and makes
every change at once.

A `fetch_claims` row is the lock that keeps two replicas from downloading one artifact: the
fetcher inserts it before the download and deletes it after the ingest, or after a failure, in
transactions of its own. It beats every 30 seconds, and a row whose `heartbeat_at` is older than
2 minutes is stale: a fetch of the artifact takes it over, and `reindex` and the reconcile loop
delete it. It is not a `tag_claims` row: the digest is unknown until the download ends, and the
ingest inside the fetch takes its tag claims as every publish does. `ResetDerived` does not touch
it.

`proxy_meta` is a cache of the upstream, not of the registry: reindex neither reads nor writes
it, `ResetDerived` leaves it, it needs no backup (a backup of the database holds it, stale after
a restore), and dropping it costs upstream requests and nothing else. A row's expiry is not
stored: it is `checked_at` plus the repo's TTL of its state, read when the row is. A write of a
row invalidates the repo's `index_cache` rows of the name in the same transaction.
Expired `absent` rows are deleted once a minute, with the expired sessions.

An `oci` proxy's rows (proxy-and-group.md §11.3) keep the upstream's tags, the exact bytes of the
manifests and indexes it fetched (until and after the backend holds them), what each lists, what
the backend holds, at which paths it holds each blob, and whether its tags move. Its `oci.ref`,
`oci.held`, `oci.holders` and `oci.fixed-tags` rows are present and have no TTL; a write of one
does not invalidate `index_cache`, which an `oci` proxy does not have. Their loss costs a `HEAD`
per tag and a counted `GET` per manifest or index the backend does not hold, a fetch of each blob
that the backend held at another path only, and makes the tags of a backend whose tags do not
move answer until a push is refused again.

A proxy repo has `packages`, `versions`, `files`, `index_cache` and `oci_repos` rows as a hosted
repo has, rebuilt by reindex from its manifests; the `attrs` of a proxied version hold its
`lajstrom.origin.*` annotations too. An `oci` proxy has `oci_repos` rows only, as a hosted `oci`
repo. A group has none of them, nor `proxy_meta`, `fetch_claims`
or `tag_claims` rows: reindex and the reconcile loop pass it by, and its documents are merged
from its members' on every request (proxy-and-group.md §8.5). `group_members` is control plane:
a backup of the database keeps it, and reindex neither reads nor writes it.

An apt group is the one group with `index_cache` rows: the documents it renders from its members'
versions, under its own `repo_id`, scope the suite and kinds those of a hosted apt repo
(proxy-and-group.md §8.6). They are derived from the members' rows, rebuilt lazily as a hosted
repo's, and invalidated with the members' ([below](#the-generation-of-a-repos-documents)).

A `versions` row exists only after the registry accepted the manifest and served it back (the
visibility barrier, [registries/README.md](../registries/README.md#consistency)); the claims in
`tag_claims` are the locks that serialise the writers of one OCI repository across replicas,
and a claim older than `ingest.claimTTL` is stale: ingest takes it over, `reindex` and the
reconcile loop delete it. A claim is keyed by the package path, as the registry keys the
manifest. Names that differ only in ASCII case (maven `Com.Example:lib` and `com.example:lib`,
raw `Docs/Readme.MD` and `docs/readme.md`) have one package path, so one OCI repository and one
set of tags, and a package path has one spelling: the first one published
(`packages (repo_id, name_oci)`, #244).

A publish takes two claims, first in its transaction, before the registry write: the claim on
the package path (tag `''`, digest the sha256 digest of the spelling), then the claim on its
tag (the manifest digest); on a registry that folds the case of tags
(`provider.Capabilities.TagsFoldCase`) the claim's tag is the tag lower-cased, so that two tags
that differ only in case, one tag there, are one claim (manifest-profile.md §4.2). After them it reads the package of the package path and the version
of the tag, so a concurrent writer of the tag, or of another spelling, waits for the first
one's commit and then sees its outcome. Every publish takes the two in this order, so two
publishes never wait on each other crosswise. A claim with the same digest is shared: on a tag,
two replicas publishing the same bytes; on a package path, the publishes of one spelling. A
fresh claim with another digest is a `409`: on a tag, other bytes; on a package path, another
spelling being published. A package of the package path with another name is a `409` naming
that name. A publish refused by a claim or by the package pushes no manifest. An upload of a
frontend whose tag a fresh claim of another digest holds takes that claim's manifest over when
the registry has it with the same name and file layers: the retry of a publish that the
visibility barrier answered `503`, which keeps its claims, built again with another
`org.opencontainers.image.created`. An upload whose tag is made of its file's bytes (raw, the
first 16 hex digits of the sha256; `format.Built.ContentTag`) is a publish of the same file as
any fresh claim of its tag. When the registry does not serve the claim's manifest, the claim's
publish is on its way or stopped before its push, and the upload waits for it, up to
`ingest.visibilityTimeout` (or the registry's `consistencyBound` when that is longer), reading
the claim and the registry again: a version of the tag with the same files is the idempotent
repeat, a claim released or stale is the upload's to take, a claimed manifest that the registry
serves is taken over as above (one of other files is the `409`). A claim still held at the end
is `503` with `Retry-After: 30`, and the upload pushes nothing. Any other upload refused by a
claim whose manifest the registry does not serve gets the `409` at once.

The transaction that writes the derived rows releases both claims; from then on the package
row holds the package path. A publish that stops before that releases the claim on its tag and
leaves the claim on the package path to go stale, for another publish of the spelling may share
it. A publish that stops before it sends its manifest to the registry, and whose release the
database fails (a database out, which also failed its pending audit row), leaves its claim to
its process, which releases it again every second until the database answers or the claim is
half `ingest.claimTTL` old; a process that stops before that leaves it to go stale. A claim
whose manifest was sent, or that was taken over from another publish, is not released again. A publish that shares a stale claim on a package path makes it again (deletes the row and
inserts its own, in its transaction), so that the claim is not taken over while the publish
runs. `ResetDerived` does not touch claims. A replica of an earlier version keys its claims by
the spelling and takes no claim on the package path. Its rows are released or go stale as
before and need no migration, but during a rolling upgrade the claims of the two versions do
not exclude each other, and the check of the tag in the backend before the push is the one
guard between them.

A `reindex_runs` row in state `running` is the lock that keeps two runs of one repo apart across
replicas and the CLI. Starting a run takes a transaction lock of its own
(`pg_advisory_xact_lock` with the reindex key on Postgres, the write lock of `BEGIN IMMEDIATE`
on SQLite) and, under it, refuses a run when a running row overlaps it: a run of every repo overlaps every run, a run of one repo overlaps a run of every
repo and a run of the same repo. A running row whose `heartbeat_at` is older than the stale bound
(2 minutes; the run beats every 30 seconds) is closed as `abandoned` by the start that finds it,
and the new run starts. `done` is a run that went to the end, whatever its report lists;
`failed` one that stopped on an error of its own (the registry or the database unreachable, the
process shut down). Finishing a run deletes the finished runs of the same scope beyond the ten
newest.

A `replicas` row is a `serve` process on the database: written at its start, after the
migrations, beaten every 30 seconds and deleted when it stops; a row whose `heartbeat_at` is
older than 2 minutes is of a process that is gone, and the next start deletes it. The CLI's
commands write none. On SQLite, which serves one replica (its referrers and journal locks are
locks of the process), the start is a transaction that holds the write lock of the file, and a
row of another replica with a fresh heartbeat refuses it: `serve` exits with an error that
names that replica (id, host, process, version, start, last heartbeat) and when its row goes
stale. A process that crashed or was killed leaves its row. When the row is of the starting
process's host and of its scope, the boot and the PID namespace in `process` (Linux: the
`boot_id` and the PID and time namespaces; macOS: `kern.bootsessionuuid`), and its PID names no
process or one that started at another time (Linux), the process is gone: the start deletes the
row and goes on. On Linux and macOS `serve` also takes, before it writes its row, the
`flock(2)` lock of `<file>-replica.lock`, a file it creates next to the SQLite file, and holds it
until it stops; its row's `flock` names that file when it took the lock (another process holds
it, or the file system takes no lock: `''`). The kernel drops the lock when the process ends, so
a start that took it and finds a row of its boot (the `boot=` field of `process`) whose `flock`
names the same file knows the row's process gone, whatever its host name and PID namespace: the
start deletes the row and goes on. Otherwise (another host or boot, a container restarted in a
new PID namespace whose row held no lock or another file's, a row with no `process`) `serve` on
the file is refused until the row is stale, 2 minutes after its last beat at most; an
orchestrator that restarts it on failure starts it then. A replica that
stood still for that long finds its row deleted at its next beat and writes it again; on SQLite, while another replica's row is fresh,
that is refused, and `/-/readyz` answers `503` until it is not. On Postgres the rows of every
replica coexist. At its start and at every beat a replica also compares its clock with the
database's (`DatabaseTime`; [operations.md](../operations.md#clocks)), as `reindex` and `admin`
do before they run.

A `prune_sightings` row is the registry's answer `404 MANIFEST_UNKNOWN` to the digest of an index
row's manifest (`Provider.StatManifest`, `provider.ErrManifestUnknown`), which reindex waits on
before it removes the row: it removes it only on another such answer at least 10 minutes after
`first_at` (Invariants and rules; guarantees.md, INV-5). A sweep records an answer
(`Writer.RecordSighting`, which keeps `first_at`) and, once it has looked up every row it did not
see, clears the repo's rows it did not record again (`Writer.ClearSightings`): a manifest that read
back, a lookup that failed, a row that is gone. The table is operational state, not derived:
reindex never rebuilds it and never needs it to rebuild the derived tables, `ResetDerived` leaves
it, and it needs no backup. Losing it only delays a removal by one more answer. The rows are
keyed by the registry's manifest, not by an index row, so that one answer counts for every
replica: runs of one repo never overlap (`reindex_runs`), and the 10 minutes keep two runs of
two replicas' loops that follow each other from counting as two answers. Approved by the lead on
2026-11-11 (#446).

The referrers lock has no table. The `sha256-<hex>` tag-schema index of a subject is a
read-modify-write of one tag, and OCI has no compare-and-swap for manifests: two referrers
attached at once through two replicas can each write an index without the other's. Ingest holds
the referrers lock of (OCI repository, subject) for the push of a referrer when the provider keeps
the tag-schema index (`Capabilities.TagSchema`: the backend has no referrers API, or the registry's
`referrers.alwaysTag` is on), and everything the push does to the index
happens under it (`Store.WithReferrersLock`): on Postgres `pg_advisory_xact_lock` on a key hashed
from both, in a transaction held for the push; on SQLite, which serves one replica, a lock of
the process. With the referrers API alone the registry keeps the list, and a referrer pushed to an
`oci` repo by digest takes no lock; a referrer of a managed repo takes it all the same (below).
Approved by the maintainer on 2026-11-09 (#28).

On Postgres the lock lasts as long as its transaction, and the transaction idles while the push
talks to the registry. Whatever ends the transaction earlier ends the lock: another writer takes
it while the push still runs (#615). So the statement that takes the lock also sets
`idle_in_transaction_session_timeout` to 0 for the rest of the transaction
(`set_config(…, true)`, in the same round trip), and the transaction ends with a `COMMIT` whose
result is checked. When the transaction was ended before (a timeout the client cannot lift, a
terminated backend, a failover), `WithReferrersLock` returns an error wrapping
`index.ErrUnavailable`, never nil, and the client gets `503` with `Retry-After`. The error comes
after the push: a writer that held the lock meanwhile may have written the index without this
referrer, or this push the index without that writer's. The retry reads the index under the
lock again and adds its own referrer when it is missing; the other writer's, which succeeded, is
not restored, and nothing reports it. So no timeout that the client cannot lift may end
Lajstrom's transactions: a pooler's (PgBouncer's `idle_transaction_timeout`) stays 0, its
default, and so does Postgres's `transaction_timeout` (version 17 and later, which counts active
time too) for Lajstrom's users. The migration and reindex locks hold their transactions across
database statements only, and their commits are checked. Any lock held across work outside the
database takes the same two steps, and its test runs with a short
`idle_in_transaction_session_timeout` (`TestReferrersLockLost`).

The same lock is the **tag lock** of a manifest: the referrers lock of its subject when it has
one, else the lock keyed by its own digest. A delete through ingest holds it while it counts the
tags of the manifest and deletes it (http-routing.md §2, DELETE: a delete by tag of a manifest
that other tags name is refused), and a push by tag to an `oci` repo, which passes through to
the backend, holds it for the push; both whether the backend has the referrers API or not. A tag
pushed during a delete is then either counted by it or pushed after it. One operation takes one
such lock, never two, since `WithReferrersLock` holds a connection of the pool, with the one
exception below. Approved by the maintainer on 2026-11-10 (#284).

A delete writes its rows in the index, and its audit row, before it releases its lock, so that
the writer that takes the lock next reads the index without the version (#72). A conditional
delete of an npm version (`format.Condition`, http-routing.md §4) takes two locks, in one order:
first the package's journal lock (the lock keyed by its OCI repository and the empty blob's
digest, [the journal](#the-journal-and-its-state-npm-and-pypi-adr-0012) below), then, inside
it, the tag lock of the manifest. Under the journal lock it reads the package's dist-tags, and a dist-tag move, which
checks under the same lock that the version it names exists, comes either before the delete,
which then refuses the version, or after its rows are gone, and is refused itself. **The order
is the journal lock before a tag lock, never the other way**: nothing waits for a journal lock
while it holds a tag lock. A journal append, the delete of a journal entry and reindex's journal
pass take the journal lock alone; a referrer push, a push by tag and every other delete take a
tag lock alone. So two operations never wait on each other crosswise. On Postgres the delete
holds two connections of the pool for the locks and a third for the transaction of its rows, as
a journal append holds one for its lock and one for its transaction: when the pool is
exhausted, a delete that waits for a connection waits until one is free or its request ends.

On a managed repo a referrer's subject must be a manifest of the repository (http-routing.md §2,
PUT). Ingest checks it before any lock, then pushes the referrer under the referrers lock of its
subject, with the referrers API or without, and resolves the subject again under the lock before
the push: refused, `400 MANIFEST_INVALID`, when the backend does not have it any more. That lock
is the tag lock of the subject when the subject has no subject itself, a version's manifest, and
the delete of the version holds it while it lists and deletes the referrers, the manifest and
its rows. A referrer pushed during the delete of its subject is then either deleted with it or
refused after it, and never stored for a version that is gone, nor its `sha256-<hex>` index
written again (#806). So the referrer pushes of one subject follow each other with the API too;
an `oci` repo, which takes a referrer whose subject does not exist (the distribution spec),
keeps the rules above. A referrer of a referrer (a countersignature) is not covered: its push
takes the lock of its own subject, and the delete of that subject, or of the version above it,
holds the version's.

The **package row** is the last lock of the order. Every version write and delete
(`UpsertVersion`, `DeleteVersion`) locks its package's `packages` row first, in the transaction
it runs in, until that transaction ends (#570): the version writes of one package follow each
other, and `packages.created_at` sees what the writers before committed. A delete takes it in the
transaction of its rows, inside its journal and tag locks; a publish takes it in the transaction
that confirms the version, under no lock of this section; reindex in the transactions of the
rows it writes. No transaction that holds a package row waits for a journal or a tag lock:
`WithReferrersLock` is never called inside `Store.Tx`. So the order is the journal lock, then a
tag lock, then the package row, and a conditional delete that holds the first two waits for the
row only as long as another writer's transaction of the package runs.

### Pages of packages and versions

The management API pages a repo's packages and a package's versions (http-routing.md, `GET
…/packages` and `…/versions`) with two keyset queries of the Reader, so that a page reads its
own rows and not the whole list (#552). `ListPackages` and `ListVersions` stay for the callers
that need every row: the renderers, reindex, ingest.

- **`ListPackagesAfter(repoID, prefix, after, limit)`** returns the packages of the repo whose
  name starts with `prefix` and comes after `after` (`""`: from the first), ordered by name, at
  most `limit` of them. It is `name > after ORDER BY name LIMIT limit` on the unique index
  `(repo_id, name)`; when the prefix comes after `after`, the scan starts at the prefix.
- **`ListVersionPage(packageID, after, limit)`** orders the versions of a package by their key,
  `VersionKey`: the earliest `created_at` of the version's rows (the publish time of its first
  variant), then the version string, both descending. It returns the rows of the first `limit`
  versions whose key comes after `after` in that order (nil: from the newest), every variant
  of each; a version's rows are together, ordered by variant. The database groups the
  package's rows by version (`MIN(created_at)`, over the unique index `(package_id, version,
  variant)`) and answers only the page's rows.
- **`ListVersionFacts(versionIDs)`** answers what the list of versions shows of each variant
  beyond its row (#1132): of each of the given `versions` rows, its `files` rows counted and
  their sizes added up, and its `attachments` rows counted by `kind`. One statement for up to
  500 ids, the two groupings joined by `UNION ALL`, over the indexes `files (version_id, name)`
  and the unique `attachments (version_id, digest, layer)`: a page costs one statement, not one
  per row.
- **The order is byte order.** Names and version strings compare as bytes: every text column is
  `COLLATE "C"` on Postgres (and on YugabyteDB, which runs its migrations), has no collation on
  CockroachDB, which compares strings by their bytes by default, and is `BINARY` on SQLite,
  which is the order of Go's `strings.Compare`, the one the API's cursor compares with.
  Timestamps compare at the stored precision, microseconds; SQLite's text form has a fixed
  width, so its text order is time order.
- **A key is a place, not a row.** A page after a key holds the rows after it in the order the
  database has then: a package or version inserted before the key is on no later page, one
  inserted after it is on the page that reaches it, and a deleted one, the key's own
  included, is on none; nothing else repeats or is skipped. A variant added to a version with
  a `created_at` earlier than its first moves the version's key, and that version may then
  repeat or be skipped, as it would between two reads of the whole list.
- **`limit`** bounds the packages, or the versions, of a page; one below 1 returns none. A
  caller asks for one more than its page to know whether another page follows.

Both read unique indexes the schema has; they need no migration.

### The package list, one package and search

The package list with its parameters, one package and the search (http-routing.md §4; #955,
#958, #956) read four more methods of the Reader, each a fixed number of statements:

- **`ListPackagePage(repoID, PackageQuery)`** returns a page of the repo's packages that the
  query keeps (a prefix, a text, attrs), in its order (by name, the newest manifest, the count of
  versions or the size; ascending or descending) after its key, at most its limit, each with its
  key: the name, and the value of a sort other than by name. By name, with no filter but the
  prefix, it reads a range of `(repo_id, name)`, as `ListPackagesAfter`. A sort other than by
  name, a text and attrs read every package of the repo: the values of a sort are grouped once
  over the repo's versions rows, and their files for the size, and joined with the packages;
  the text compares `name` and
  `versions.summary` folded with `LIKE` and an escape, the folding `lower` on SQLite and
  Postgres, whose text columns are `COLLATE "C"` and so fold ASCII letters only, and `translate`
  of the 26 letters on CockroachDB, whose `lower` folds others too; attrs read `versions.attrs`
  by key, `json_extract` on SQLite and `->>` on Postgres and CockroachDB. The page keeps the rows
  after the key as a row comparison, `(value, name) > (?, ?)`, or `<` descending.
- **`ListPackageFacts(packageIDs, latest)`** returns for each package the counts of its versions
  and manifests, the size of its file layers, the publish time of its newest manifest, its last
  published version (the first by `VersionKey`), its latest version, which the caller's `latest`
  picks among its versions with the package's journal state (the format's order lives in the
  plugin, http-routing.md §4), with that version's variants, the dist-tags of its journal state
  that name one of its versions, and its head row (the first variant in byte order of the latest
  version, else of the last published one) without `metadata`: five statements over the rows of
  the packages, the counts, the sizes, the distinct versions with their first publish times, the
  journal state, and the rows of the versions picked.
- **`ListAttrValues(repoID, key)`** returns the values of a key in the repo's `versions.attrs`,
  each with the number of packages that have it, in byte order: the store sorts them, since `->>`
  answers text in the database's collation on Postgres.
- **`Search(SearchQuery)`** returns the hits of one rank of the search after a key, at most its
  limit, over a set of repos (or every repo), in the order of `(repos.format, repos.name,
  packages.name, versions.version, versions.variant, files.name)` as far as the rank has them. A
  digest's prefix is a range of `versions_digest` or `files_digest` (`digest >= 'sha256:<hex>'
  AND digest < 'sha256:<hex>g'`: `g` comes after every hex digit); a name or a summary reads every
  package of the repos, folded as the text above.

The sorts other than by name, the text, attrs, facets and the search by name read rows in
proportion to the repo, or to the repos searched, and no index serves them; the search by digest
and the page by name do not. On a repo of 10 000 manifests in 1 000 packages, a page of 100
packages with their facts, a facet, and a search over two such repos each take at most 20 ms on
SQLite and on Postgres (`storetest.Bench`, `BenchmarkPackageList`).

### The summaries of the rows before 0029

Migration 0029 adds `versions.summary` NULL. `serve` fills it in the background when it starts,
on every replica, from the `metadata` the rows keep (#954): `ListVersionsWithoutSummary` reads
the rows whose `summary` is NULL and whose `metadata` is not, 25 at a time in `id` order after
the last one read; the summary of each is computed as ingest computes it (manifest-profile.md
§2), and `SetVersionSummaries` writes the batch in one transaction, `''` for a manifest without
one, to the rows whose `summary` is still NULL. It is the same statements on the three engines.
Two replicas that fill at once write the same values; a row that ingest or reindex wrote
meanwhile keeps theirs; a row deleted meanwhile is skipped. Its log says how many rows it read
and wrote, and how many have a summary; a failure is logged and stops it until the next start.
A row whose `metadata` is NULL (omitted for size, or degraded) keeps NULL until a reindex with
`verify` reads its manifest again.

### The generation of a repo's documents

A document is rendered lazily, in a transaction that reads what it renders from and then stores
it; an invalidation is part of the transaction of the change. On Postgres, in read committed,
a render that began before an invalidation could store its document after it, and that stale
document stayed until the next invalidation of the repo. So every invalidation of a repo's
`index_cache` (`InvalidateIndexCache`, of one scope or of all, and `ResetDerived`) first
increments the repo's row of `index_cache_generations`, then deletes the documents. A render
reads the generation before anything it renders from (`IndexCacheGeneration`), and the store
of its documents (`PutIndexCache`) first writes the generation row as it is, which takes the
row's lock, and stores them only when the generation is still the one the render read;
otherwise the render is answered and not stored. The row's lock orders the two: a store waits
for an invalidation that holds it and then reads its generation, and an invalidation that comes
after a store waits for it, so that its `DELETE` sees the stored rows. On SQLite every
transaction holds the write lock from its start, and the two never interleave.

The generation is per repo: an invalidation of one scope also refuses the store of a render of
another scope that it overlapped, which renders again on the next request. During a rolling
update from a release before 0017, the invalidations of the older replicas do not increment it,
and their renders do not check it.

An invalidation of a repo that is a member of groups is theirs too: `InvalidateIndexCache` and
`ResetDerived` of the repo increment, in the same transaction and before any `DELETE`, the
generation of the repo and of every group it is a member of, in the order of their ids, and
delete the groups' documents of the same scope; `SetGroupMembers` increments the group's and
deletes all of its documents. Only an apt group keeps documents (proxy-and-group.md §8.6); for a
group of another format the increment changes nothing.

  package's scope; the whole repo's, as the delete path does, is correct too. A group's

### Attachments (#89)

The signatures, SBOMs, scan reports, provenance and other attestations of a version: the
attachments of its referrers (manifest-profile.md §6.1), one row per attachment, labelled with
their verification (§6.3). The table is derived: the referrers in the registry are the truth,
and reindex rebuilds it from them. Nothing else in the database records a result: there is no
table of record of scans (#89, decision 1).

| Table | Columns | Notes |
| --- | --- | --- |
| `attachments` | `id`, `version_id` → versions (`ON DELETE CASCADE`), `digest` text (the referrer manifest's), `tag` text (cosign's legacy tag, `''` for a referrer pushed by digest), `layer` text (the digest of the attachment's layer, `''` for a manifest without layers), `media_type` text (the layer's; for a manifest without layers its artifact type), `artifact_type` text (the manifest's `artifactType`, else its config's media type), `kind` text (`signature`, `sbom`, `scan`, `provenance`, `attestation`, `other`: §6.1), `predicate_type` text (`''` when none), `size` int (the layer's), `annotations` json (the manifest's), `tool`, `tool_version`, `database`, `input` text (the `lajstrom.attachment.*` annotations, else for the first three what the statement's predicate names, §6.2; `''` when neither), `verification` text (`verified`, `untrusted`, `unsigned`, `invalid`, `unsupported`: §6.3), `signed_by` text null (the `name` of the key or keyless identity that verified it; null unless `verified`), `reason` text (why it is not verified, `''` when it is), `trust` text (the hash of the trust that labelled it, `attest.Trust.Hash`), `created_at` ts null (the referrer manifest's `org.opencontainers.image.created`; null without one), `indexed_at` ts (when ingest or reindex last wrote or saw the row) | unique `(version_id, digest, layer)`; index `attachments_digest` on `(digest)`. - **Writers.** Ingest, reindex and delete, never a frontend or the API:

  - The delete of a referrer removes its rows (`DeleteAttachments`), in the transaction of its
    audit row. A version's rows go with it (`ON DELETE CASCADE`), and so does
    `DeletePackage`'s and `ResetDerived`'s.

- **Best effort on a push.** A push succeeded when the registry served the referrer back
  (http-routing.md §2). A failure to read its layers or to write its rows afterwards is logged

- **References.** A row whose `input` is the `digest` or the `layer` of a row of another
  referrer of the same version (a scan report and the SBOM it was computed from) keeps that
  referrer: its `DELETE` on `/v2` is `409` while the row is there (http-routing.md §2), so a job
  that prunes attachments (#72, keeping the first and the last N per predicate type) keeps an
  SBOM while a report it keeps names it; the delete of the version takes both. The rule reads
  these rows: a report whose rows are not written yet (best effort, above) keeps nothing until
  they are (#89).
- **Versions without an attachment.** `ListVersionPage` with attachment kinds keeps the
  variants that have no row of any of them (`NOT EXISTS` on `version_id` and `kind`, over the
  unique index), for `?without=` (http-routing.md §4).

### A repo's stats

The `stats` of a repo in the management API (http-routing.md §4, #957) are counts of the derived
tables, so that reindex rebuilds them. **`RepoStats(repoIDs)`** returns, for each repo of
`repoIDs` that has a package, its rows of `packages`, its distinct `(package_id, version)` of
`versions`, its rows of `versions`, their rows of `files` with the sum of `files.size`, and the
newest `versions.created_at`: a fixed number of statements grouped by `packages.repo_id`,
whatever the number of repos, over the unique indexes `(repo_id, name)` of `packages` and
`(package_id, version, variant)` of `versions` and the index `(version_id, name)` of `files`. A
repo without a package has no row, and its counts are 0. It needs no migration.

### The mapping of an encrypted repo

An encrypted repo ([manifest-profile.md](manifest-profile.md) §11, ADR 0009) stores ciphertext,
and the facade answers each client in the form it pushed (http-routing.md §2.1). One table maps
the digests a client knows to those the registry has, and keeps what a read needs to decrypt a
layer without reading its manifest.

| Table | Columns | Notes |
| --- | --- | --- |
| `blob_map` | `id`, `repo_id` → repos (`ON DELETE CASCADE`), `path` text (the package path, as `packages.name_oci`, of the OCI repository that holds the blob or the manifest), `kind` text (`blob`, `manifest`), `plain_digest` text (the plaintext's digest: a layer's, or the digest of a manifest as the client had it), `stored_digest` text (the ciphertext's, or the stored manifest's), `size` int (the blob's, the same in both forms; the stored manifest's), `key_fingerprint` text (`''` for a manifest: the `enc` key that `wrapped` opens with), `wrapped` text (`''` for a manifest: the private options wrapped for that key, the value of `org.opencontainers.image.enc.keys.jwe`, or of a keys referrer's member), `pubopts` text (`''` for a manifest: the value of `org.opencontainers.image.enc.pubopts`), `indexed_at` ts | unique `(repo_id, path, stored_digest)`; index `blob_map_plain` on `(repo_id, path, plain_digest)`. Migration `0031_blob_map.sql` |

- **Writers.** The facade, ingest, reindex, delete and the rotation, never a frontend:
  - the close of a blob upload of the facade writes the row of the blob (`kind` `blob`), a mount
    from another path of the repo the row at the target path, and the file of a publication
    session (maven, an apt source upload) the row of its file as it is stored;
  - ingest writes the rows of a manifest it stores, the manifest's and each encrypted layer's, in
    the transaction that indexes it: a version's, or a referrer's once the registry serves it
    back;
  - the delete of a manifest removes its row, in the transaction of its rows; the rows of its
    layers stay, which another manifest at the path may name, until reindex;
  - a rotation sets `key_fingerprint` and `wrapped` of a layer's rows when its keys referrer is
    served back.
- **Reads.** A layer's row is found by `(repo_id, path, stored_digest)`, the decryption of a
  frontend's file read; a plaintext digest by `(repo_id, path, plain_digest)`, the facade's. Two
  rows of one plaintext digest at a path are two uploads of the same bytes: any of them answers.
- **Reindex** writes the rows of every manifest it reads, its own and its layers'. The wrapping
  is the newest keys referrer's for the layer (manifest-profile.md §11.1), else the manifest's
  annotation; reindex opens it with the repo's key, which it needs to learn the plaintext digest.
  A pruning run then removes the rows of the repo that no version, file or attachment names and
  that it did not write, but those of `kind` `blob` written less than a day before it, the
  longest a publication session lives (`maven.sessionTimeout`): a blob uploaded and not yet named
  by a manifest. A run without the master key, or whose seals of the repo's keys do not open, or
  that has no client for a KMS that holds one, skips the repo whole and leaves its rows; a KMS
  that refuses or does not answer during the run fails the manifests it was asked for, which keep
  their rows ([operations.md](../operations.md#encryption-at-rest)).
- **Rebuilt, not trusted.** A row only says where to look: a read checks the HMAC and, where it is
  known, the plaintext digest of what it decrypts, and a push checks that the registry has the
  ciphertext.

## Snapshots of the control plane

A snapshot (#76; [manifest-profile.md](manifest-profile.md) §9) is the control plane written into
the registry, so that a database lost without a backup comes back from it: `lajstrom admin
snapshot create` reads the tables and pushes them, `lajstrom admin snapshot restore` writes them
into an empty database, and `lajstrom reindex` rebuilds the derived tables after it.
`index.Snapshotter` reads and writes them; both engines implement it beside `Store`, which serve
uses and which does not have it.

| Table | In a snapshot |
| --- | --- |
| `repos`, `group_members`, `users` (the deleted ones too, with `owner`, `last_seen_at`, `must_change` and `password_history`, without `password_failures` and `locked_until`: a restore unlocks every user), `identities`, `identity_groups`, `tokens` (the deploy tokens over a mask too, with `repo_mask`), `bindings`, `keys`, `webhooks`, `policy_rules` (#101), `ci_policies` (#937) | every row, with its id |
| `audit` | the rows of a window that the operator asks for, every row, or none (the default) |
| `bootstrap_token` | no: serve makes one at its start while no enabled user has an admin binding |
| `approvals` | no: a request waits 7 days at most, and the audit rows hold every request and decision (rbac.md §5); a restore drops the requests that wait, which are made again |
| `config_state` | no: it is the configuration of the servers that ran on the database, not one to restore; a forced restore empties it, and the next start records its configuration with `initial` (rbac.md §5) |
| `sessions` | no: their clients start them again, as after a restore of a backup |
| `webhook_deliveries` | no: the outbox and the delivery log of the events before the snapshot. A restore sends none of them, the pending ones included, where a restore of a backup sends those again |
| `auth_version`, `schema_migrations`, `policy_state` | no: the restore increments `auth_version` and `policy_state.generation`; the document's `schema` is the newest migration |
| coordination, derived (`attachments` and `verdicts` among them, and `versions` with its `oci_repo`), `policy_seen` | no: their rows live for one operation, or reindex rebuilds them: the attachments from the referrers in the registry |

A control-plane table or column that a later migration adds is in the snapshot, with that
migration, unless this table says why not.

- **Ids are kept.** A token refers to its user and repo, a key to its repo, a group member and an
  identity to their rows, and `token:<id>` is the principal of bindings, audit rows, a webhook's
  `created_by` and `lajstrom.uploaded-by`: the rows come back with the ids they had, and the
  references stay true. A user is `user:<uid>` everywhere, and its `uid` comes back too.
- **No secret in clear.** The tables hold none, and the snapshot carries them as they are:
  `users.password_hash` (argon2id), `tokens.hash` (sha256 of the secret), `keys.private_enc` and
  `webhooks.secret_enc` (encrypted with the master key; a webhook's with its `uid`, which comes
  back with it, as the additional data). `bootstrap_token` is not carried. The master key, the
  registry passwords, the DSN and the OIDC client secret are never in the database.
- **One moment.** `ExportControlPlane` reads every table in one transaction, `SERIALIZABLE, READ
  ONLY, DEFERRABLE` on Postgres and YugabyteDB, and returns before anything talks to the registry:
  no transaction is held across a request to it. Every token's user and repo, every key's repo and
  every member's group are in the same read. Such a transaction reads one snapshot and is never
  aborted; on YugabyteDB it waits out the clock skew, where a repeatable read under writes fails
  with "restart read required".
- **Into an empty database.** `ImportControlPlane` writes into a database whose tables of the
  first two rows above are empty, all of them; a table that has a row makes it fail with
  `ErrNotEmpty`, naming the tables, and change nothing. A `serve` started on the database once is
  enough to fill two: it makes the configured repos and the bearer-token key. Forced, it empties
  every table but `schema_migrations`, `auth_version` and `replicas` first, in its transaction:
  the derived rows of the repos go with them, and reindex writes them again. `lajstrom admin
  snapshot restore` also refuses while a `replicas` row has a heartbeat younger than 2 minutes: a
  replica serving on the database would keep its snapshot of the bindings and write beside the
  restore.
- **One transaction.** The rows are inserted with their ids in one transaction, every table in the
  order of its references, and the restore's own audit row (`snapshot.restore`) comes last in it.
  On Postgres the sequence of each table's id is moved past the greatest id restored, and never
  back, so that the next insert does not collide: with `nextval` alone, which the data rights of a
  database user for serve allow (`USAGE` on the sequences; `setval` needs `UPDATE`;
  [operations.md](../operations.md#a-database-user-for-serve)), the values taken being gaps.
  SQLite's next rowid follows the greatest. `auth_version` is incremented in the same transaction.
  The restore runs with serve's database user, as every admin command does.
- **Versions.** A snapshot of a `schema` newer than the newest migration of the binary is refused,
  `ErrSchemaTooNew`, and nothing is written. One of an older `schema` is written as it is: a
  column added since takes its default, as expand migrations require (Upgrades). The exception is
  `users.last_seen_at`, which a snapshot of before 0034 does not have: the restore fills it as
  that migration does, with the time of the restore for a user with a password, so that a
  restore makes no user inactive that the migration would not (rbac.md §1). The database
  itself must be migrated to the binary's schema first (`lajstrom migrate`), as for every admin
  command.
- **Not the export of ADR 0015.** That export (its point 15, not built) writes the declarable
  objects, repos and bindings, in the schema of the declarative sources, without ids, for review
  and GitOps; users, tokens and keys are not in it. A snapshot is for disaster recovery: row for
  row, ids and secrets' hashes included, in a document of its own.
- **No table of its own.** A snapshot needs no migration: the registry holds it, and the audit
  rows `snapshot.create` and `snapshot.restore` record what was written and restored.

above. The runner,
`index.ApplyMigrations`, applies each pending file in a transaction of its own that also records
the version in `schema_migrations` (created when missing). The transaction first takes the
migration lock, `pg_advisory_xact_lock` on Postgres and `BEGIN IMMEDIATE` on SQLite, and reads
`schema_migrations` under it, so replicas that start at once apply each version exactly once.
A transaction that fails on a conflict with another schema change is rolled back and run again
from the start, up to five times in all, after a pause that doubles from 100 ms, with a warning
each time (#616): one that the database aborted, `40001` from any of its statements (YugabyteDB
aborts DDL that conflicts with another schema change, also in another schema,
[yugabyte-db#21833](https://github.com/yugabyte/yugabyte-db/issues/21833)), and a `42710` from
the create of `schema_migrations` (YugabyteDB: a migrator that waited for the lock does not see
the table that another committed meanwhile). The retry reads `schema_migrations` again under the
lock, so it applies a version at most once; it is correct where DDL is transactional (Postgres;
YugabyteDB with the flag of [databases.md](../deploy/databases.md#yugabytedb)). Every other
error, a `42710` from a migration file among them, ends the run at once.
`lajstrom migrate` and `lajstrom serve` (on start) run it. When no migration is pending, it
runs no statement that changes the schema. A migration file is never changed once a release
has it: the runner records only its version, so a fix is a new migration.

**On CockroachDB a migration is not one transaction** (#617). There an `UPDATE` does not see a
column added earlier in its transaction, and the commit of a transaction with DDL can fail
after its other statements committed (`XXA00`), which would record a version whose DDL is
missing. So the runner applies a cockroach file one statement at a time, each in a transaction
of its own, and records the version after the last one. The migration lock is
`pg_advisory_xact_lock`, held by a transaction on a second connection of the pool from before
the read of `schema_migrations` to after the record, so that it spans those transactions without
a session lock; a pool of one connection is refused. A statement that CockroachDB aborts
(`40001`) runs again, five times in all. A migration that stops half-way (an error, a crash,
`XXA00`) is not recorded: the error names the statement, and the next run applies the file
again from its first statement. So every statement of a cockroach file may find its work done:
`CREATE … IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `DROP … IF EXISTS`, `INSERT … ON
CONFLICT`, or an `UPDATE` or `DELETE` that computes its rows from what it finds; statements end
at a semicolon at the end of a line, comments are on lines of their own, and a test checks
these forms. The replicas that serve during the migration see its statements take effect one
by one, which the rules of [Upgrades](#upgrades) allow: an expand migration only adds what
release N leaves alone or reads as before, and a contract migration removes only what N does
not use. The cockroach files 0001 to 0025 run on an empty database only, since no release
migrated a CockroachDB database before them, and leave out what the Postgres files do to rows
that cannot exist there: 0008 adds `users.uid` `NOT NULL` without filling it. Every later
migration has a cockroach file, written for rows.

## Upgrades

During a rolling update the replicas of two releases share one database: release N+1 (its
first replica, or `lajstrom migrate`) migrates the schema while the replicas of release N still
serve on it, and a rollback runs release N on the schema of N+1. So every migration is one of
two kinds.

**Expand** (the default): release N runs on the schema after it. It adds a table, an index, or
a column that is nullable or has a default the database fills; it adds a constraint that every
row release N writes meets; it fills or rewrites rows only where release N reads the result as
it read the rows before. A unique index that release N's inserts may violate, or a backfill of
values release N does not understand (0009 rewrote `user:<name>` to `user:<uid>`), is not
expand.

**Contract**: everything else: a dropped or renamed table or column, a changed type, a column
made `NOT NULL`, a constraint that release N's writes do not meet. A contract migration removes
only what the release before it no longer uses, so it comes at least one release after the
change that stopped using it, and its leading comment has the line

```sql
-- lajstrom:requires NNNN
```

where NNNN is the first migration of the release that stopped using what it removes: every
binary that knows NNNN runs on the schema after it, and no binary that uses it knows NNNN. A
release that stops using a table or column and has no migration of its own adds one that only
records its version (a file with a comment only). A rename is an added column, written beside
the old one for as long as a release that reads the old one may run, and a contract migration
that drops the old one later. The runner records NNNN in
`schema_migrations.requires`, so a binary that does not know the migration knows what it
requires. Every dialect declares the same (a test asserts it).

**What a binary tolerates.** So that release N runs on the schema of N+1, and N+1 on the rows
N writes during the update:

- Statements name their columns: no `SELECT *`, no `INSERT` without a column list. Tables,
  columns and indexes a binary does not know are left alone.
- A value it does not know in a column of a fixed set (`kind`, `state`, `role`, `source`, a
  principal's prefix) fails the request that reads the row, or skips the row, and never stops
  the replica or rewrites the row.
- A field added to a `json` column has a meaning when absent: a replica of release N rewrites
  the column (`repos.policy`, `sessions.files`) without it.
- Release N+1 reads rows that N inserts after the migration: a column N+1 adds is NULL or its
  default in them, a backfill in the migration does not cover them, and N+1 reads them as N
  meant them.

**What a binary does with the schema it finds.** `index.ApplyMigrations` reads
`schema_migrations` first, at the start of `serve` and in `lajstrom migrate`:

| The database | What happens |
| --- | --- |
| no migrations | every migration is applied |
| pending migrations, none requiring more than the schema's newest version | they are applied |
| a pending migration requires more than the schema's newest version | nothing is applied, `ErrBreakingMigration`: the replicas serving on the schema may not know NNNN. `serve` on Postgres and `lajstrom migrate` refuse, exit status 1; `lajstrom migrate --allow-breaking` applies it, once the operator has stopped them; `serve` on SQLite applies it, for it is the only replica |
| current | nothing, and no statement that changes the schema |
| versions the binary does not know, none requiring more than its newest | it runs: `serve` logs a warning, `migrate` says so |
| versions the binary does not know, one requiring more than its newest | nothing is applied, `ErrSchemaTooNew`: `serve` and `migrate` refuse with exit status 1 and name the migration a binary must know |

There are no down migrations: a rollback is the binary of the release before on the newer
schema, which expand migrations allow; to a release older than the one a contract migration
requires, it is a restore of the backup taken before the upgrade. Every migration so far, 0001
to 0039, requires nothing; binaries built before 0014 do not check the schema. `serve` migrating
on start is the default, enough for one node; with several replicas, `lajstrom migrate` of the new
release runs once before the rolling update ([operations.md](../operations.md#upgrades)). A release with a
contract migration says so in its notes ([release.md](../release.md#migrations-in-the-notes)).
`TestUpgrade` runs the migrations of four releases against one database on each engine: an
expand migration, the marker, a contract migration, a rollback, and an upgrade that skips a
release.

## Invariants and rules

- Every row in `packages`, `versions`, `files` corresponds to a manifest that exists in the
  registry with a tag; reindex adds rows for manifests it finds and, when the run prunes, removes
  rows whose manifest is gone. Every run drops the whole `index_cache` of each repo it scanned to
  the end, pruning or not.
- `packages`, `versions`, `files`, `journal`, `journal_state`, `attachments` and `verdicts` are
  written only by `ingest` (a publish, a journal append, a referrer push, a delete) and `reindex`; frontends
  read them. `index_cache` is stored
  by the render of a `GET` (a frontend, the proxy core) and invalidated by the writers above, a key
  rotation, a write of `proxy_meta` and the purge of a proxy's cache. `oci_repos` is written by
  ingest, reindex and the facade, for a push to an `oci` repo; `proxy_meta` by the proxy core and
  the purge of a proxy's cache ([above](#proxy-and-group-repos)).
  Ingest claims the package path and the tag in `tag_claims` before the registry write, and
  writes the derived rows after the registry accepted the manifest, in one transaction that
  also releases both claims.
- Unique constraints implement the append-only tag rule: an insert that violates
  `(package_id, tag)` with a different digest is a `409`.
- A foreign manifest (no `lajstrom.schema` annotation) under a managed path is recorded in
  `oci_repos` only and reported by `reindex --report`, never indexed. A manifest with `subject`
  is a referrer, not a foreign manifest: reindex counts it and reports it as an orphan when no
  version has its subject's digest; an image index under a `sha256-<hex>` tag is the tag-schema
  referrers index (manifest-profile.md §6). Neither is a row of its own: a referrer of a version
  is the rows of its attachments ([Attachments](#attachments-89)), and the index itself none.
- Reindex never starts from `ResetDerived`: it marks and sweeps. Every row it writes or sees gets
  the run's time in `indexed_at`; a tag whose manifest has the digest of the index row, in a row
  that is not degraded, is seen without being read again (the same digest is the same bytes,
  checked when it was written), unless the run verifies. At the end, when the run prunes (the
  sweep), each row of the repo not seen since the run started is looked up by its tag in the
  OCI repository of its manifest (`oci_repo`, else its package's `name_oci`) once more: a tag that names the row's digest keeps it (written after the listing,
  possibly by a replica whose clock is behind), a tag that names another digest is drift (below),
  and a tag the registry does not
  resolve asks for the manifest by its digest (`Provider.StatManifest`). Only `404
  MANIFEST_UNKNOWN` counts as unknown, and the row goes only on the second such answer at least
  10 minutes after the first (`prune_sightings`, Coordination) and when its `indexed_at` is at
  least `reconcile.graceAge` old (guarantees.md, INV-5); packages left without versions go with
  it. Any other answer (`NAME_UNKNOWN`, a `404` without the code, a `5xx`, `401`, `403`, a
  timeout) keeps the row and is an error of the report, but one: a `404` without
  `MANIFEST_UNKNOWN` in an OCI repository whose tag list is a `404` too, which the registry does
  not know (deleted in its console: Zot's `NAME_UNKNOWN`), keeps the row and lists it under
  `repositoryUnknown`, with the request of the management API that deletes it, on every run
  until then (#567); a run asks each OCI repository's tag list at most once. A run that cannot
  list the repo's OCI repositories sweeps nothing. The sweep drops an `oci_repos` row when no
  run has seen its repository for `reconcile.graceAge`, and every run drops an `oci` repo's at
  once when its tag list has no tag (below); a sweep that finds a version's manifest records its
  repository again.
- A tag that names another digest than the index row of that tag is drift: the index keeps its
  digest, the report lists both, nothing is re-pointed (the rule of the reconcile loop, #30).
  A drifted row is the one row whose manifest is not under its tag any more.
- A package whose manifests are at two forms of its package path (ADR 0017: one written before
  it, one after, while the index lacked the earlier) is a split. A package has one `name_oci`:
  the index keeps the form of its row, or, for a package it does not have, the newest form
  found, the form ingest writes such a package to (a run reads the newer forms first), and every
  write of the package goes there. A version found at the other form is indexed all the same,
  with that form in `oci_repo`, and every download, delete, `/v2` tag list and recheck of the
  version goes where its manifest is (`index.ManifestPath`, #642). A version that is at both
  forms has one row: at the indexed form when the manifest there is the row's (a copy) or when
  the index has none yet (a run reads the indexed form first from an empty index), else where
  the index has it; a tag at the other form is then not indexed, and a tag at the indexed form
  with other bytes than the row's is drift. The report lists both forms and the tags at each
  (`split`), on every run until the other form is gone. Nothing is copied or moved in the
  registry: an operator who wants the package at one OCI repository copies the other form's
  tags into the indexed one and deletes the other form (operations.md), and the next run moves
  each copied version's row to the indexed form (#609).
- A repo of format `oci` (pass-through, http-routing.md §1) has rows in `oci_repos` only: the
  facade records the repository of every manifest pushed to it, after the registry took the
  manifest, and nothing else is indexed. Its `oci_repos` records only the repositories that hold
  a tag, which its catalog lists (#748): Zot keeps a repository whose manifests are all deleted,
  and its tag list answers `200` with no tag. A delete that leaves the repository without a tag
  (an empty tag list, or `404`) drops its row (`Store.DeleteOCIRepo`), and so does reindex when
  the repository's tag list is empty. A push into the repository may race the drop, so the row
  goes first and the tags are listed once more after it, without a lock: a tag pushed before the
  row went is in that listing, and the repository is recorded again, as it is when that listing
  fails; a push after it records the row itself, after its manifest. Meanwhile the catalog may
  miss the repository for one tag list's time. A managed repo's rows stay the registry's
  repositories, as its delete leaves them; its catalog lists its packages.
- The control plane is backed up with the database
  ([operations.md](../operations.md#backup-and-restore)), and can be snapshotted into the
  registry at `lajstrom/control-plane` ([below](#snapshots-of-the-control-plane), #76). There is
  no JSON export besides (`lajstrom admin export`, acceptance.md G-07, is not built).
